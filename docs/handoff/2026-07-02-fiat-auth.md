**For:** a fresh-context agent. **Goal:** spec and build crystal's **identified fiat** login rail —
username/email + password with **email verification** and password reset — minting a session that
the rest of `/v1` already knows how to verify. This is JS-nuke blocker #11
(`docs/plans/2026-07-02-js-nuke-readiness.md`). It is **largely greenfield** (legacy had only web3
login), so this is a *design + build*, not a port.

## Ground rules
- **Crystal TypeScript only.** End green (`tsc`, `test:crystal`, `test:hermetic`, docs-drift). No
  `Co-Authored-By`. Prefer `fix:`.
- **Crystal-first:** reuse the `Persona`→`Anima` bridge; do NOT add a new identity store for the
  soul. The new state is *credentials* (email/hash/verify tokens), not a new identity.

## The full auth model (map — so you see where fiat fits)

Crystal resolves every caller to an `AuctorKey` (`{animaId}|{commitment}|{bursaToken}`) at the `/v1`
boundary. Rails that exist **today** (verified 2026-07-02):

| Rail | Credential | How | Identity | State |
|---|---|---|---|---|
| Anonymous | `x-commitment` header | self-asserting, accepted as-is (`IdentityResolver.ts:80`) | `{commitment}` | ✅ |
| Bursa purse | `x-bursa-token` / body | short-circuit in `apiRouter.auth()` before IdentityResolver | `{bursaToken}` | ✅ |
| Web3 wallet | `body.web3{address,signature,nonce}` | injected `verifyWeb3` acceptor → `{animaId}` | `{animaId}` | ✅ (acceptor) |
| API key | `x-api-key` | injected `validateApiKey` → `{animaId}` | `{animaId}` | ✅ (validate only) |
| CAMEL federated | `Authorization: Bearer` ES256 | JWKS acceptor (ADR-0011) → `{animaId}` | `{animaId}` | building |
| Bearer session JWT | `Authorization: Bearer` HS256 | `verifyJwt` (`apiAcceptors.ts:89`) validates `JWT_SECRET` tokens → `{animaId}` | `{animaId}` | verify ✅, **mint ✗** |
| **Fiat username/password** | email + password | **THIS HANDOFF** — register/verify/login → mint session JWT | `{animaId}` | **build** |

**Key fact:** `verifyJwt` already *validates* any HS256 token we sign with `JWT_SECRET` — so the
new work is **issuance + credential storage + email**, not verification.

## What's missing (verified)
- **No session minting** anywhere in crystal (only `verifyJwt`/`jobToken` HMAC). Legacy `authApi.js`
  minted a web3 session cookie — no username/password/email flow to port.
- **No email/mailer infrastructure** in crystal *or* legacy. Email verification/reset needs a mailer
  — a genuine net-new dependency (below).

## The seam
- `resolveOrCreateAnima(personae, animae, genus, externusId)` (`apiAcceptors.ts:48`) mints Anima +
  Persona on first sight for a `(PersonaGenus, externusId)`.
- `PersonaGenus` union at `src/types/persona.ts:22` — **add `'password'`**. `Personae.findOrCreate`/
  `findByExternus` (`persona.ts:79`).
- `verifyJwt` resolves a bearer token under genus `'web'`, `externusId = payload.userId/sub`
  (`apiAcceptors.ts:98`).

## Net-new infrastructure: an email sender
Email verification + password reset require sending mail — **none exists**. Add a minimal
`Mailer` seam (`send({to, subject, html})`) with one implementation behind an env-configured
provider (Resend / Postmark / SES / SendGrid — pick one, API-key via env, no secrets in code) and a
`NoopMailer` for hermetic tests/dev (logs the link). Keep it a thin injected interface like the
other acceptors — do not couple auth to a specific vendor.

## Data
A small `Credentials` store (keep `Persona`/`Anima` pure):
```
Credential {
  id, email (unique, lowercased), passwordHash,           // argon2id (preferred) / bcrypt
  animaId,                                                  // the resolved soul
  emailVerified: boolean,
  verifyToken?: string, verifyTokenExp?: Date,             // single-use, ~24h
  resetToken?: string,  resetTokenExp?: Date,              // single-use, ~1h
  createdAt, updatedAt
}
```
(A `'password'` Persona `externusId = email` links to the Anima; the hash/tokens live on
`Credential`, not the Persona.)

## Flows to build (`createAuthRouter`, mount `/v1/auth/*` + compat `/api/v1/auth/*`)
1. **`POST /auth/register`** `{ email, password }` → validate email + password strength → hash →
   `resolveOrCreateAnima(..., 'password', email)` → persist `Credential` (`emailVerified:false`,
   `verifyToken`) → **send verification email** → `202` (no session yet; account exists but
   unverified). Duplicate email → generic `409` (avoid enumeration).
2. **`GET/POST /auth/verify-email`** `{ token }` → look up by `verifyToken` (unexpired, single-use) →
   set `emailVerified:true`, clear token → mint + return session JWT (auto-login on verify).
3. **`POST /auth/resend-verification`** `{ email }` → new token + email; always `202` (no enumeration).
4. **`POST /auth/login`** `{ email, password }` → verify hash (constant-time). **Policy decision:
   require `emailVerified` before login?** Recommend: allow login but gate spend/paid actions on
   verified, OR block login until verified — pick one and state it. On success mint session JWT.
   Generic failure message; rate-limit by IP+email.
5. **`POST /auth/session/refresh`** → re-mint from a valid unexpired session.
6. **`POST /auth/forgot-password`** `{ email }` → issue `resetToken` + email; always `202`.
7. **`POST /auth/reset-password`** `{ token, newPassword }` → validate token (unexpired, single-use)
   → re-hash → invalidate existing sessions if feasible.

**Session shape:** mint `jwt.sign({ sub: <animaId>, typ:'session' }, JWT_SECRET, {expiresIn})`.
Decide **bearer vs cookie**: the crystal React app sends headers (`anonHeaders`), so **bearer
`Authorization`** is the natural fit (legacy used an httpOnly cookie — don't inherit that unless the
web app wants cookies). State the choice.

## ⚠ The one integration trap — resolve the SAME Anima on both sides
`verifyJwt` resolves a bearer token under genus `'web'` with `externusId = payload.sub`. The session
you mint at login/verify **must** resolve (via `verifyJwt`) to the **same Anima** the `'password'`
Persona established, or login and subsequent requests split into two accounts.
**Recommended:** mint `sub = animaId, typ:'session'` and extend `verifyJwt` to treat a
`typ:'session'` token's `sub` as a **direct `animaId`** (skip the `'web'`-genus re-resolution).
Prove it with the acceptance test below.

## Security
argon2id (or bcrypt ≥ cost 12); never log/return hashes; constant-time compare. Verify/reset tokens:
≥128-bit random, single-use, short TTL, stored hashed. Login + resend + forgot rate-limited; generic
messages (no user enumeration). Email links over HTTPS with expiry. `JWT_SECRET` server-only. Email
normalization (lowercase/trim). Consider disposable-email blocking later (not v1).

## Acceptance
- Register → receive verification email (NoopMailer logs link in tests) → verify → session JWT → an
  authed `/v1/me` resolves to the **same Anima** as registration (credits granted at register are
  visible after login) — proves the same-Anima trap is handled.
- Login: correct password + verified → success; wrong password → generic fail; unverified → per the
  stated policy; duplicate register → generic 409.
- Forgot → reset token email → reset-password → login with new password works; old password fails.
- Expired/reused verify/reset tokens rejected.
- Anon `x-commitment`, bursa, web3 rails unchanged (fiat is additive).
- `tsc`/`test:crystal`/`test:hermetic` green; hermetic tests for every flow + the same-Anima invariant
  (using `NoopMailer` + `MemorySignorum`).
